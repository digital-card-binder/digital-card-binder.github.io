# 디지털 카드 바인더 — 5~6차 품질·성능·백업 운영 가이드

## 1. 5차: 기존 이미지 검수 결과 보존

- 기준 브랜치: 병합 시 최신 `main`.
- `npm run images:audit`는 카드 코드 중복, 이미지 경로, 이미지 아카이브 연결을 정적으로 검사합니다.
- `npm run images:triage`는 기존 아카이브 변환 대상이 아닌 이미지 URL을 출처·세트별로 **분류만** 합니다.
- 결과는 GitHub Actions **Verify** → `catalog-quality-<run-id>` 아티팩트의 두 JSON 파일에 보관합니다(14일).
- 이미지 URL이 아카이브 라우팅 대상이 아니라는 사실만으로 이미지가 깨졌다고 판단하지 않습니다. 공식·제3자 출처, 기존 Cloudflare 주소, 로컬 이미지, 잘못된 경로를 구분해야 합니다.
- 실제 이미지 그림, 인쇄 번호, 카드명이 일치하는지는 별도 한국판 근거 검수 대상입니다. 이전 검수 완료 기록을 폐기하거나 자동으로 이미지 주소를 교체하지 않습니다.
- **차단 기준**: 카드 DB 중복, 아카이브 누락, 실제 참조한 로컬 파일 없음 등 구조적으로 입증 가능한 오류. 단순 미인식 도메인은 조사가 끝날 때까지 경고로만 남깁니다.

## 2. 6차: 2만 장 검색

- 통합 검색은 한 검색 결과 집합을 최초 1회 정렬한 뒤, 동일 결과의 시대·세트·보유/미보유 필터 변경 시 재정렬하지 않습니다.
- 검색어가 바뀌거나 카드 결과 배열이 교체되면 자동으로 재정렬합니다.
- 결과 정렬·카드 식별자·보유 상태 저장 로직은 변경하지 않습니다.
- `tests/phase5-6-image-search-backup.test.mjs`에서 21,100개 가상 카드로 반복 필터 및 결과 배열 교체를 검증합니다. 이 테스트는 성능 회귀 방지 테스트이며 실제 PC/스마트폰 렌더링 시간 보장은 아닙니다.

## 3. 계정별 백업·복원 안전 절차

**운영센터 관리자 로그인**에서 백업 JSON 파일을 내보낸 뒤 다음을 확인합니다.

1. 최신 사이트에 로그인한 상태인지 확인하고 백업 파일을 직접 생성합니다.
2. 파일 이름과 생성 날짜를 확인하고 오프라인 드라이브 등 **비공개 위치**에 중복 보관합니다. 파일에는 소유 기록 및 커스텀 바인더 정보가 들어갈 수 있으므로 GitHub 공개 저장소, 이슈, 공개 채팅에 업로드하지 않습니다.
3. 복원할 때는 **같은 계정**으로 로그인한 상태에서 파일을 선택합니다. 사이트는 지원 형식, UID, 도감 문서, 분할 보유 기록, 이미지 조각 크기 및 Firestore 쓰기 크기를 **쓰기 전에 사전 검증**합니다.
4. 복원 버튼을 눌러도 최종 확인 전에는 DB에 쓰지 않습니다. 복원은 기존 데이터를 변경할 수 있으므로, **사용자가 복원을 명시적으로 승인한 경우에만** 진행합니다.
5. 정기 백업은 월 1회 및 대규모 변경 전에 별도로 수행하는 편이 안전합니다.

자동 테스트는 가상 계정/파일로 실패 안전성을 확인하며, **실제 회원 Firestore 데이터 백업을 자동으로 생성하거나 복원하지 않습니다.** GitHub 데이터 커밋과 GitHub Pages 배포는 Firestore 회원 기록의 백업이 아닙니다.

## 4. 운영 안정화 기준

- GitHub Pages 배포와 Verify 통과를 별도로 확인합니다.
- Cloudflare 이미지 건강 점검의 온라인 WebP 샘플 통과는 전체 이미지가 확인됐다는 증거가 아닙니다.
- 커뮤니티 공개 동기화는 별도 변경 작업이므로, **동기화 담당 브랜치 변경을 덮어쓰지 않도록 작업 시 최신 `main` 기준을 재확인**합니다.
- 이전 감사 산출물 및 수백 개 역사적 워크플로는 근거 없이 삭제하지 않습니다. 새 기능보다 재현 가능한 실패 수정과 간결한 운영 절차를 우선합니다.
