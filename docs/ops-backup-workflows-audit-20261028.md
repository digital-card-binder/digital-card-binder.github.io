# 디지털 카드 바인더 — 운영센터 백업·GitHub Actions 정리 점검

점검일: 2026-10-28 · 변경 목적: 데이터 손실 없는 운영 안정화 · 기준: v32 이후 `main`.

## 1. 운영센터 백업·복원 확인

### 실제 코드 확인
- `operations.html`은 관리자 로그인 완료 후에만 기능 사용 가능. `operations.js`는 `accountCore.isOwner`로 소유자를 판별.
- 실제 Firestore 계정 문서 8종(`nationalDex`, `packDex`, `artistDex`, `seriesDex`, `pokemonCollectionsDex`, `arDex`, `trainerPokemonDex`, `worldDex`) 및 시리즈/AR 분할 보유 문서, 현재 커스텀 바인더의 활성 이미지 조각, 계정별 월드 로컬 상태를 포괄.
- 백업 시 `getDocFromServer` 및 `getDocsFromServer`만 사용. 네트워크 오류를 오래된 오프라인 캐시 백업으로 숨기지 않음.
- 백업은 `digital-card-binder-backup-v2`, 스키마 2와 사용자 UID를 기록. 파일 복원 시 다른 계정·미지원 문서·비정상 샤드·이미지 조각 수/용량·과도한 배치 크기 거절.
- 실제 복원은 별도 파일 선택 → 구조/용량 사전 검증 → 관리자 확인 대화상자 → 승인 후에만 Firestore 쓰기 수행.
- 백업 생성 직전에도 **동일한 `validateBackup(payload)`를 호출**하도록 수정하여, 구조 검증을 통과하지 못한 파일을 사용자에게 정상 백업으로 제공하지 않도록 보강.
- 재현 테스트: `tests/stabilization-ops-backup-workflows.test.mjs`에서 정상 백업·실패 시 다운로드 차단·계정 불일치·잘못된 도감 키·손상 샤드 검사.

### 접근 및 검증 범위 한계
**실제 사용자의 Firebase 계정에서 원격 문서를 읽거나 백업 JSON을 직접 생성한 것은 아님.** 자동화에서는 모의 데이터로만 백업 생성/검증을 시험. 운영 중인 계정 데이터를 건드리지 않기 위해 실데이터 복원 테스트나 Firestore 쓰기는 수행하지 않음. 서버 저장값의 실제 사용자별 데이터 정합성은 사용자 본인이 운영센터에서 백업 파일을 만들어 별도 보관하고 관리자 건강검진 결과를 확인해야 확정 가능.

백업 JSON에는 개인 보유 정보가 포함될 수 있으므로 공개 GitHub 저장소·이슈·채팅에 원본을 업로드하지 말 것. GitHub Actions는 이 계정의 백업 파일을 자동 생성하지 않음. Git 브랜치 스냅샷은 Firestore 사용자 데이터 백업이 아님.

## 2. GitHub Actions 전수 목록

`scripts/audit-workflow-inventory.mjs`로 **워크플로 파일 597개를 정적 검사**(새로운 보고서 전용 워크플로 1개 포함). `on:` 이벤트와 푸시 대상 브랜치/경로 필터, `contents: write` 권한을 분류. 파괴적인 변경 **0개**.

| 분류 | 개수 | 처리 |
|---|---:|---|
| 운영 핵심 보호 대상 | 7 | 유지, 교체 입증 전 금지 |
| `main` 쓰기 권한 추가 검토 | 536 | 경로 필터/트리거/실행 기록을 따로 검증 |
| `main` 이벤트와 연결된 기타 | 22 | 현재 서비스와 관련된지 개별 확인 |
| 과거 브랜치 전용 | 31 | 분리 후보, 실제 의존성 확인 전 삭제·비활성화 금지 |
| 수동 실행 전용 | 1 | 사용처 확인 필요 |
| **합계** | **597** | **597개 모두 보존** |

별도 지표: `main` 트리거가 설정된 워크플로 564개, 이 가운데 `contents: write` 표기가 있는 워크플로는 538개. **이 수는 현재 실행 중인 작업 수가 아니며**, 조건에 맞는 코드 변경이나 수동 실행이 없으면 실행되지 않을 수도 있다. 자동화와 휴면 여부를 판별하려면 실제 GitHub Actions 최근 실행 기록·워크플로별 `paths:`·브랜치 존재 여부를 추가 확인해야 한다.

주요 유지 대상은 `verify.yml`, `watch-official-card-updates.yml`, `sync-site-versions.yml`, `deploy-card-images.yml`, `deploy-firestore-rules.yml`, `radar-live-smoke.yml`, `build-android-apk.yml`. 이외 GitHub의 Pages 빌드/배포 기능은 호스팅에 필수.

### 감시와 정리 정책
- 기존 공식 카드 업데이트 감시는 매일 1회 유지.
- `audit-theme-*.yml`, `xy-*.yml` 등 지난 검수 워크플로 상당수는 `main`에 쓰기 가능. 파일명에 예전 날짜가 있어도 직접 삭제·비활성화하지 않고 기록 보존 및 사용 여부 점검 대상.
- 불필요한 과거 워크플로를 제거하려면 **실제 최종 실행일**, 현재 브랜치 존재, 의도치 않은 실행 경로, 이전 감사 산출물 의존성, 복구 절차, 필수 secret 및 배포 권한을 확인한 후 별도 PR에서 묶음 단위로 정리.
- 백업·운영 검사용 신규 Actions는 인벤토리 작업에 `contents: read`만 부여. 별도 검증 job은 해당 작업 브랜치에 한정하여 정적 캐시 참조만 동기화하도록 관리.

### 검증 산출물
`.github/workflows/operations-v32-inventory.yml` 실행에서 `v32-workflow-inventory` 아티팩트로 **전체 597개 파일의 이름·트리거·분류·쓰기 권한과 Markdown 정리 후보 목록**을 다운로드할 수 있음. 이 보고서는 GitHub Actions 아티팩트에 보관되며 실제 YAML 삭제/수정은 수행하지 않는다.

## 3. 결론 및 다음 안전한 작업

- 현재 긴급히 제거해야 할 사용자 데이터·카드 데이터는 발견되지 않음.
- 백업 형식 사전 검증을 추가하고 운영센터 비파괴 테스트를 보완.
- Actions는 파일 전체 목록을 분석·보고했으며, 현재 서비스 필수 작업의 보존을 우선하여 제거·비활성화 없음.
- 권장 후속은 사용자가 운영센터에서 **실제 백업 JSON을 생성해 비공개로 보관**하고 `health.html` 경고를 확인하는 것. 실제 DB 쓰기를 수반하는 복원은 사전 승인 없이는 수행하지 않는다.
